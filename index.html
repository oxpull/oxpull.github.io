One fewer service to run

Tasks are rows in the database your application already runs. A management command runs the worker. You still deploy and monitor a worker process. You do not add a broker to run background tasks.

A killed worker's task returns

With LOCK_TIMEOUT 15 s, django-ox finished 2,000 of 2,000 tasks in every kill trial (20 kills each). django-tasks-db left 13 to 19 stuck RUNNING. Default recovery bound: about 330 s. At-least-once: effects repeated 7 times in 10,000 tasks, so make them idempotent.

Commit tasks with application rows

enqueue() is one INSERT. Inside transaction.atomic() the task commits or rolls back with the rows beside it. A broker cannot share that transaction. There is no window where an order exists without its email task. Keep the queue and those models on one database.

Measured, not promised

django-ox is benchmarked against django-tasks-db, the other database backend for Django's Tasks API. Both run on the core Tasks API, against the same PostgreSQL database, on the same machine. Every cell is five runs, and every run behind a published figure is on the page, not a best pick. A worker-death test kills a worker process 20 times per trial and counts what each backend does with the tasks it was running. The benchmarks page carries the method, the figures and the raw files.

The benchmark task bodies do nothing, so the rates measure framework overhead. Read them as relative, not as capacity planning. The API stability page states what counts as public API and how versions change.
